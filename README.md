# Tornado Cash — New Era

A local-first Tornado Cash interface built with Vue 3 and TypeScript, using the Kohaku SDK (`@kohaku-eth/tornado-cash`). The current release is available on IPFS at bafybeifsqylni6qcznv2b27gymbymruqhmhp6kjy2sp6hafz3iqq3ezmha.

## Run

```sh
nvm use
npm ci
npm run prepare:offline
npm run dev
```

Open the printed local URL. `npm run build` creates a static site in `dist/`. `npm run preview` serves that production build locally. Deploy the **whole** output, including `withdraw-frame.html`, fonts, and `sdk/` workers. Production hosting must use HTTPS. No backend or API secrets are bundled.

`npm run prepare:offline` obtains checksum-pinned public assets once, reusing matching local pool snapshots and the CLI's installed proving files when available. It writes the ignored `offline-assets/` directory and public deployment metadata in `src/core/history-bootstrap.json`. It accepts an optional local directory containing `tornado.json` and `tornadoProvingKey.bin`. Subsequent builds need no history/artifact server while these files are present. A saved release’s dist/offline/ directory can also be copied to offline-assets/ before preparing; the same checksum checks apply. Missing or modified offline assets stop the build rather than producing an incomplete deployment.

`npm run build:ipfs` creates the upload-ready `dist/` directory, including compressed history, relayer-registry history and proving files under `offline/`. Upload/pin that whole directory, with `index.html` at the CID root. These assets are loaded on demand, not on the landing page. Relative asset paths support HTTPS path gateways (`/ipfs/<CID>/`), CID subdomains and DNSLink; open directory URLs with the trailing slash. Hash navigation (`#multi-withdraw`, `#smart-account`) needs no SPA fallback or rewrite rules. Use an HTTPS gateway, preferably a CID subdomain for origin isolation. Local HTTP gateways on localhost also work; opening `index.html` directly with `file://` is unsupported. A live Ethereum/Sepolia RPC and a working bundler or Classic relayer are still needed to transact. IPFS hosting does not hide network requests or IP addresses.

```sh
npm run typecheck
npm test
npm run build
```

## Current scope

- One deposit cart with minus/count/plus controls per denomination, itemized quantity × denomination subtotals, and an exact running total. There is no session note cap. Wallet batches contain at most 12 ETH notes or 5 ERC-20 notes, plus required token approvals. Each batch confirms before the next starts; wallets without native batching send sequential transactions.
- Ethereum mainnet and Sepolia. Mainnet ETH denominations: 0.01, 0.03, 0.1, 0.3, 1, 3, 10, 30, 100. The SDK has no Sepolia 100 ETH deployment, so that option is unavailable there.
- **Both deposits and withdrawals** use the same catalog/paymaster-allowlist intersection as kohaku-cli. Mainnet: ETH, DAI, USDC, USDT, WBTC. Sepolia: ETH, DAI. cDAI and other deposit-only pools are excluded.
- Independent, Classic-compatible notes by default. An optional deposit-form toggle generates a fresh 24-word BIP-39 phrase for that deposit session and includes it with every raw note in the required text backup. Withdrawals accept raw notes (one in the basic flow, 1–12 in the separate smart account flow); there is no phrase import or persistent note vault.
- Wallet connections are opt-in on every page load. Startup only listens for passive provider announcements: no account/network/capability requests, automatic connection restoration, or legacy injected-provider access. Opening the wallet chooser discovers wallets; selecting one requests accounts. After explicit connection, account changes and balances continue to update.
- Required note download and backup acknowledgement before a deposit can be sent. The cart and checkout show the paying wallet’s ETH balance and selected ERC-20 balance. Insufficient-balance warnings are advisory; users can change or disconnect the paying wallet and return to the same backed-up checkout without regenerating notes. Balances refresh on account/network/token changes, on return to the tab, every 30 seconds while active, and on request.
- Injected EIP-1193 / EIP-6963 wallet discovery. Native atomic batching through EIP-5792 when advertised, with sequential wallet transactions otherwise. ERC-20 approvals request the exact amount for each batch, with allowances reread after the preceding batch confirms. USDT-style nonzero allowances are reset first. No application-driven EIP-7702 delegation of the deposit wallet.
- **Basic withdrawals: exactly one note at a time.** The default route is one SDK-prepared, paymaster-sponsored ERC-4337 UserOperation. Pasted/imported multi-note files are rejected in that flow; there is no withdrawal queue. Withdrawal proceeds and unused-gas refunds go directly to the reviewed recipient. Empty calldata and zero execution gas are enforced before review and submission, so the EIP-7702 sender does not take custody of funds. The UI uses the SDK's recoverable note-derived sender default rather than random delegation. No connected withdrawal wallet or recipient private key is required in the basic flow. An optional Classic TORN relayer route sends one transaction directly to the recipient; custom actions are available only in the separate smart-account flow.
- Pimlico and Custom bundler options. Configure endpoints in Settings. The chain and EntryPoint v0.8 are checked before preparation and submission. An advertised EntryPoint alone does not prove that a provider will accept a particular operation; the SDK first attempts estimation and permits its bounded best-effort fallback for the direct single-note path when estimation is unavailable.
- Classic relayers are discovered through the SDK registry/ENS/stake checks and must advertise the selected pool. The review separates the network fee from the relayer service surcharge, showing its percentage and amount, with a “Switch to 4337?” action. No simultaneous 4337 quote is generated. Service rates must be below 1%; the SDK’s 20% total-fee and token-price-deviation limits remain active. Mainnet registration history reuses seven pinned, checksum-verified files from the external artifact service, followed by the SDK RPC tail. Sepolia uses its configured registry. Unavailable relayers or unsupported denominations produce an explicit error.
- A review shows full-note value, proof-bound fee, recipient, and net proceeds. The adapter checks zero execution gas, empty calldata, the direct recipient, pool, chain, paymaster, and proof data before a 4337 broadcast. Classic submission rechecks current stake, ENS endpoint, reward address and service rate, sends one POST without retries, and tracks the returned job ID. Confirmation requires a matching pool Withdrawal event in a successful receipt from the configured chain RPC.
- Per-call deposit progress and single-UserOperation withdrawal progress. A partial deposit failure stops the remaining batches. Status checks reconcile only the submitted batch or transaction and leave future notes unsubmitted. No automatic retries after a submission error; submitted hashes/batch identifiers remain available for receipt checks and a downloadable session record.

For withdrawals, select the note's network, paste one Classic note (or import a text backup), enter the recipient, and choose/configure the bundler. Text-file imports extract only Tornado note strings; seed phrases, section headings and metadata never populate the withdrawal field. All extracted notes retain their original order and still go through the normal network, asset and duplicate checks. The basic flow rejects files containing multiple notes rather than selecting or queuing one. Review the fee and net proceeds, then confirm the one UserOperation. Finish or check a pending submission before reviewing another note.

## Smart account withdrawals and custom actions

The app still opens on Ethereum mainnet with Deposit selected and one 0.01 ETH note in the cart. After every deposit call is confirmed with a transaction hash, **Start a new deposit session?** clears the finished session and restores one 0.01 ETH note, keeping the connected wallet and network. The next checkout generates new secrets and requires a new backup; pending sessions cannot be cleared with this action. The single-note withdrawal panel links to `#multi-withdraw`, a separate flow for 1–12 notes of one asset. It uses the SDK’s `delegation: { mode: 'smart-account' }` with eth-infinitism SimpleAccount **v0.8.0**. The connected EOA signs only `eth_signTypedData_v4` during withdrawal; no private key, `personal_sign`, or EIP-7702 authorization is requested. Gas refinement may request several typed-data signatures. Starting preparation opens those wallet prompts sequentially without another in-page click per signature; the later request depends on the preceding gas estimate. Final fee review and submission remain separate. Only actual wallet/context changes invalidate the session; unchanged wallet wrappers during page updates do not.

After a completed withdrawal, the primary **Start new withdrawal** button clears the finished session, restores the default payout and focuses an empty note field. Preparing the next batch rereads the account and its current EntryPoint nonce. Pending or unknown submissions must still be resolved before starting over.

Multi-withdrawals and account management require an EOA controller. A contract-wallet connection is rejected by those views; a delegated EOA can still control the app’s separate SimpleAccount, with its delegation flagged as a privacy warning. No connected-account-as-sender routing is enabled. Before preparation/submission, yellow privacy warnings separately cover the smart-account sender, controller EOA and forwarding recipient (shared addresses are checked and displayed once). They flag deployment, EntryPoint nonce and current ETH balance/transaction nonce/code, as applicable. Reuse remains possible; freshness is not a hard requirement, and dust does not lock out a controller or recovery. Reads prefer the connected wallet on the selected network and fall back to the configured chain RPC. Missing reads are explicitly marked incomplete, rather than treated as zero; current zero values cannot prove there was no earlier activity or activity on other chains. Recipient edits are debounced and stale results cannot replace the current check.

UserOperation hashes link to Etherscan immediately after submission. When the bundler returns a transaction hash it is also linked immediately, even if the host RPC has not indexed its receipt yet. A missing receipt is retried; a polling timeout remains **submitted / awaiting on-chain confirmation** with both known hashes and **Check submitted operation**, rather than reporting failure or broadcasting again. Confirmation still requires the host RPC receipt’s matching EntryPoint event; an unrelated receipt or real execution failure is not converted into success.

The factory is `0x13E9ed32155810FDbd067D4522C492D6f68E5944` on mainnet and Sepolia. The factory/implementation runtime hashes are pinned to the verified v0.8 deployment. The account address is derived by `factory.getAddress(owner, keccak256("tornado-ui-new-era:withdrawal-account:v1"))`. Reconnecting the same EOA finds the same account without local storage or an extra recovery secret. Existing accounts must still have that owner, implementation and EntryPoint. The current EntryPoint nonce is read for each withdrawal; a first-use account deploys inside the UserOperation, with deployment covered by the sponsoring note’s fee.

Choose **Keep in smart account (Recommended)** (the default) or **Forward withdrawal to address**. The forwarding address starts as the connected controller’s address and can be edited to any valid nonzero EOA/contract address. For one note without custom calls, the note and postOp refund go directly to the selected recipient, with empty calldata and zero execution gas. This includes choosing the smart account itself as the recipient. Multi-note withdrawals and one-note withdrawals with custom calls fund the smart account before execution; their refunds arrive there after calls and remain recoverable. An edited destination is preserved across wallet changes and does not become the account owner; its exact address is checked before each signature and bound into either the direct sponsoring proof or the signed forwarding calldata. The current paymaster requires withdrawals with execution calls to pay the smart account first. It is recoverable, not disposable. Optional custom actions are available only when keeping funds in the smart account. Before every signature, the UI validates the factory/owner, sender, nonce, chain, EntryPoint, selected note identities, proof-bound fee, all pool calls, the optional exact forwarding call, and every byte of the reviewed custom-action suffix in order. Successful bundler estimation is required. The UI’s account-verification safety ceiling is 2M gas for first-use factory deployment and 1M for an existing account; these ceilings are not gas defaults. The SDK still refines the estimate, includes its 20% headroom, and retains other gas/fee bounds. After submission, confirmation uses the matching EntryPoint UserOperation event from the host RPC, including execution failures; unknown submissions are never automatically retried.

**After withdrawal → Add contract calls** appears only with valid notes, an explicitly connected controller and its verified smart account, and Keep in smart account selected. It opens a separate Safe-style builder without clearing the note form. Changing the actual note set, wallet/network context or payout clears calls and shows a notice; formatting-only note edits do not. The builder shows current account balances and withdrawal totals before fees, clearly marked provisional. The final review subtracts the exact maximum paymaster fee and includes existing account balances. ETH for token-withdrawal call values is shown separately; future gas refunds are excluded. Add up to 12 ordinary CALL actions using a pasted/uploaded JSON ABI and typed arguments, or a raw address, ETH value and calldata. Reorder, edit, copy or remove actions; import/export Safe Transaction Builder v1.0 JSON for the selected chain. Integers use base units, complex arguments use JSON, and ETH value uses ETH. Exports contain only public calls. Delegatecall, self-targeted account administration, malformed calldata, ABI/data mismatches and oversized payloads are rejected. Selecting Forward clears attached custom actions. Values are fixed; unspent balances and later gas refunds remain recoverable.

**Review & simulate withdrawal** prepares and signs the full operation, then calls `eth_simulateV1` through the configured website RPC (or the builder's optional simulation RPC). It executes the actual EntryPoint `handleOps`, including counterfactual deployment, sponsoring proof and remaining withdrawals, before the custom actions. Only the simulated bundler's outer ETH balance is overridden; account/token balances and storage are not fabricated. Success requires the matching inner UserOperation event, not just successful outer execution. Execution failures, out-of-gas, insufficient balance/allowance, unknown RPC errors, malformed responses and missing matching events block submission. Recognized transport failures or explicitly unsupported simulation methods are labeled **Bundler estimation passed; detailed preview unavailable**, and can continue with the required bundler estimate. Such an unavailable recheck cannot erase a known failure of the same operation; a successful preview can. Submission enforces this gate as well as the UI. Preview status is tied to the exact signed operation and expires after five minutes. Every operation still needs a separate Submit click; typed-data signatures are real authorizations even before that click.

Every prepared smart-account withdrawal now has a prominent **Simulate withdrawal** / **Simulate again** panel immediately above **Submit signed withdrawal**, including batches without custom calls and forwarding withdrawals. It rechecks the exact existing signed payload against current chain state without regenerating proofs, requesting signatures or broadcasting. Contract-call batches retain their automatic full simulation during preparation and the builder highlights that check. For withdrawals without custom calls, a detailed simulation is optional; if attempted, a failed or inconclusive result blocks submission in both the UI and submit adapter. A failed check for the same signed hash survives recalculation and an unavailable recheck. Changing the withdrawal context discards stale results. Expired reviews are visibly marked and offer **Recalculate fee & gas**; rechecking does not extend a quote’s validity. RPC simulation sends the signed payload directly to the configured simulation RPC, which may log or retain it. There is no Tenderly integration or shared simulation dashboard, and no note secrets are sent. Transfer previews and gas usage remain available when returned by the RPC.

An explicit `eth_sendUserOperation` invalid-params rejection stating that `maxFeePerGas` or `maxPriorityFeePerGas` is below the minimum is shown as **Rejected**. **Back to review** restores the same notes, recipient and contract calls; the user then reviews again to refresh gas prices, re-prove, re-sign and re-simulate. A pre-send failure also permits draft return. Changed wallet/network context still clears custom calls. Earlier attempt hashes remain in the session download. Returning to review never sends or signs automatically; submission remains a separate click, and preparation rechecks the account and note spend status. Timeouts, unknown errors, accepted operations and mined execution failures never enable this draft-rebuild shortcut. Signed candidates have already been shared with the bundler and may remain executable.

For withdrawals with execution calls, if execution reverts, the additional withdrawals and custom calls revert together, but the sponsoring note may already have been spent during validation. Its proceeds and refunds can remain in the recoverable smart account; other notes may remain unspent. Successful EVM calls do not guarantee application-level results (for example an ERC-20 returning false). Preview transfer logs are informational, not a complete asset or approval audit. Test funded withdrawal/action combinations before production use.

The **Manage smart account** view at `#smart-account` shows balances and recovery controls. Open it from the withdrawal panel and use **Back** to return; there is no header navigation link. Switching between these views preserves the withdrawal form and reviewed session in memory. The **Sweep funds to address** escape hatch works without the bundler or Tornado paymaster, even if the configured bundler URL is unavailable or invalid. Its recipient defaults to the controller and can be changed to any valid nonzero address other than the smart account itself. It sends an ordinary owner wallet transaction to `SimpleAccount.executeBatch`, routing supported token balances, ETH and any EntryPoint deposit to that recipient. The complete sweep is simulated before the wallet request. The EOA pays that transaction’s gas. This also recovers a postOp refund after successful forwarding, or sponsoring-note proceeds left after execution reverts. On execution failure, other notes may still be unspent; preserve all notes and check the receipt/account before preparing another operation. Account reuse links operations to the same owner/account, so this is an explicit custody/privacy choice.

The SDK dependency is pinned to the published `@kohaku-eth/tornado-cash@0.1.0-alpha.37` package. `npm ci` installs the SDK and its matching browser workers. The SDK routes a single note without tails directly to the requested recipient for every account family. The UI omits `tailCalls` entirely when no custom actions are reviewed. For custom smart-account calls, the UI explicitly sets `executionGasRetry: true` alongside its 8M execution-gas ceiling. A ceiling alone never enables retries. Recognizable execution-gas shortages allow up to three bounded gas probes. Each probe rebuilds the fee/proof/signature, and a successful oversized probe is tightened to the estimate plus 20% (never below the original baseline), rebuilt and successfully estimated again. Unknown reverts, validation failures, funding/allowance errors and provider gas caps do not trigger gas increases. After execution-gas recovery begins, estimation unavailability cannot downgrade the replacement to fallback. These probes do not broadcast, but send signed candidates to the bundler; the owner reviews each changed fee/signature. Basic single-note fallback remains separate. The older hidden EIP-7702 multi-withdrawal implementation remains in source, but is not wired to this page.

## Optional seed-backed deposits

The toggle below Review deposit defaults off. Enabling it creates a new 256-bit phrase using viem/scure BIP-39 and `crypto.getRandomValues`; generation fails if secure randomness is unavailable. The published SDK `SignatureSecretManager` derives notes from the signing identity at `m/29795'/1'/0'`, matching kohaku-cli. Each session starts with a new phrase and allocates one contiguous nonce sequence across every selected denomination: a four-note session uses 0, 1, 2, 3. One phrase covers every batch in a larger session; nonces continue across batch boundaries instead of restarting. An existing phrase cannot be entered or reused in this UI, so no existing-identity history scan is needed during generation.

One text backup keeps clearly labeled SEED PHRASE (SECRET) and NOTES (SECRET) sections together. A separate METADATA section explains who can spend the funds, lists note nonces in order, and links to the exact Kohaku note-derivation and seed-to-key implementations at a fixed commit. Derivation details are not copied into the file. Raw notes retain the Classic format and can be withdrawn independently. A phrase gives access to all notes in its session; a single raw note gives access only to that deposit. The session JSON also includes the phrase and recovery metadata for seed-backed deposits. Backups include all prepared notes, including any deposits that were not sent or failed; a recovering wallet discovers only on-chain deposits. Never automatically retry a submitted deposit.

The phrase and derived signer stay local to the deposit session: they are not included in wallet transaction requests, RPC calls, URLs, browser storage, or withdrawal exports. The phrase is not displayed in an input field. JavaScript cannot guarantee secure erasure of strings. CLI parity is checked against 11 fixed public vectors independently generated with the CLI's installed SDK and mnemonic keystore. An offline check through the CLI's actual discovery helper recovered all 11 notes from the phrase alone against synthetic pool history on mainnet and Sepolia, without raw-note import or external network access. Ambire's actual import/discovery flow has not been tested; another wallet must support the same Tornado signature derivation and pool catalog to discover these deposits.

## Compliance reports

The header’s **Compliance** link opens `/compliance/`. The build contains a physical `compliance/index.html`, so direct links and refreshes also work on static hosts and under an IPFS CID without a server-side SPA rewrite. Existing withdrawal hash routes are preserved.

The tool adapts Classic’s `pages/compliance.vue` and `store/application.js` (MIT, attribution in `LICENSE.classic`, also included in `dist/`). The reference checkout is `tornadocash/tornado-classic-ui` at `a83fae0772c8da084c0e76b3a756b456f5b9f5bb`; the supplied deployment hash `17c54da` was not present in that checkout. This is a Vue 3 adaptation of the same note-to-event/PDF flow, not a Nuxt bundle embedded in the page.

- Supports the interface’s full pool catalog on Ethereum and Sepolia, including the additional ETH denominations and supported ERC-20 pools. The note parser and pool metadata are shared with the deposit/withdrawal flows.
- Computes commitment and nullifier locally. Bundled history → optional Saga → RPC tail locates events; cached transaction hashes are not required. Successful receipts and matching pool logs are fetched from the selected chain RPC before displaying verified evidence. Report generation never contacts a bundler or requests a wallet signature.
- Uses current on-chain `isSpent` state at a pinned block. An unspent note has a preview and a warning; PDF export requires a verified withdrawal and explicit acknowledgement that the full note and deposit/withdrawal link will be disclosed. Nothing is stored in local storage or uploaded to a PDF service.
- Outer transaction senders are labelled as such, since 4337 deposits can be sent by a bundler. Withdrawal recipients are **pool recipients**, which may be smart accounts; the report does not claim to trace subsequent forwarding or contract calls. The fee is the proof-bound pool fee, before any paymaster gas refund.
- PDFs are produced locally with a bundled, lazily loaded jsPDF library. A reviewer can use the included note to independently derive the hashes and verify the stated pool events. The report is an informational disclosure, not legal certification or proof of ownership of an address.
- RPC/history services can see public record requests and the client IP. Raw notes and seed phrases are never part of those requests. Changing the note, network or connection settings invalidates the displayed report.

## SDK browser integration

The published SDK provides its browser loader and self-contained worker bundles. Vite serves and emits the matching worker files together under `sdk/`, preserving their sibling URLs. No dependency source patches or sibling SDK checkout are required.

The network privacy notice covers RPCs, bundlers, relayers, history and artifact downloads, and recommends Tor Browser or a VPN. Routing is supplied by the browser or network configuration, not an in-app Tor client; separate wallet traffic may need separate routing.

Each single-note review is prepared inside a short-lived same-origin iframe. Removing that document releases the SDK workers and private state after preparation; the current public SDK has no disposal method. Single-note sessions reuse sanitized public history in memory. Notes never enter URLs or external requests; proofs, public withdrawal inputs, signatures and the receiver address are sent for simulation/submission.

Chain reads prefer the explicitly connected wallet's EIP-1193 provider when it is on the selected network, with the configured HTTP RPC as fallback for unsupported methods, timeouts or an unavailable wallet. No wallet RPC URL is extracted. A separate read-only MessagePort bridge lets the disposable proof iframe and SDK use that provider. It permits only chain-read methods, pins each request to its original provider/network, checks the chain before and after reads, rejects results across chain changes, and never requests permissions, network switches, signatures or sends. Signing and submission retain their existing explicit flows.

Preparation timeouts measure inactivity rather than total elapsed time, so an active RPC-only scan is allowed to finish even when ancient history takes longer than ten minutes. A stalled session still times out, and signed estimation candidates retain the existing retry warnings.

The SDK asks for `pimlico_getUserOperationGasPrice` even when another bundler is selected. For Custom endpoints, the frontend supplies that read from standard chain RPC fee estimation. Gas estimation and submission still use the selected bundler. Single-note withdrawals try bundler estimation first, then allow the SDK's bounded best-effort fallback for recognized transport failures or estimation incompatibilities. The review identifies fallback quotes. Real validation failures remain errors; the UI never adds forwarding calls or nonzero execution gas to make estimation pass.

### External history and artifact sources

The default history sources are [Saga mainnet](https://saga.0000000000.org/) and [Saga Sepolia](https://saga.0000000000.org/sepolia/). Public snapshots and relayer registry files are available from [artifacts.0000000000.org](https://artifacts.0000000000.org/). The frontend consumes this data with the checksum, coverage and on-chain checks described above; source URLs can be changed or disabled in Advanced settings.

History first reuses fresh session memory or the checksum-verified snapshots bundled with the site. The external artifact service is a backup if a bundled file is unavailable or invalid. If both copies fail, public bootstrap metadata starts that pool immediately before deployment with empty event history; it never claims the snapshot's checkpoint without its events. A remaining older session cache can also be reused. Saga supplies newer verified history where available, followed by the RPC tail. If Saga is unavailable, RPC alone scans the remaining range, including from deployment when necessary. A cold scan can take a long time and requires a node that serves historical logs; missing/pruned logs remain errors. Failures are logged in the console and progress explains a full rescan. Only selected pool files are downloaded, with at most four concurrent snapshots. Saga v1/v2 indices and their range-bearing filenames are supported; checksums, pool addresses, ABI decoding, event ordering and contiguous coverage remain mandatory.

Proving files and mainnet TORN registry history likewise load from the site's own CID first. Proving bytes must match the SDK's exact SHA-256 pins before use, with the original commit-pinned GitHub files as an optional backup. Registry chunks retain checksum and range checks and can fall back to full RPC discovery. These external services are optional when the complete site bundle and a working chain RPC/bundler (or relayer) are available.

Settings → **Advanced: history & artifact sources** exposes per-network Saga base URLs and a shared artifact-mirror root. Both helpers can also be disabled: the app then uses bundled files plus RPC, with no Saga, artifact-mirror or GitHub backup requests. Overrides last for this browser session and retain all checksum, coverage and on-chain completeness checks. Changing sources invalidates an unsubmitted smart-account review. Source URLs accept HTTPS (or local HTTP), directory paths and IPFS gateway prefixes; credentials, query strings and fragments are rejected. A Saga URL points to the directory containing `index.json`; `/sepolia/` is explicit, not automatically appended.

A custom artifact mirror should expose these paths:

- History snapshots: `<root>/tornado-history/v1/`.
- Relayer registry files: `<root>/sync-cache/v2/saga/`.
- Proving files: `<root>/proving/`.

These files are fetched only if the corresponding bundled copy is unavailable or invalid. A custom root replaces the default remote locations, including GitHub's proving-file backup; it does not replace the pinned manifest or accept different circuit bytes. Disabling backups preserves local files and the history-to-RPC fallback. Proving still requires the exact pinned files from the site, so retain and pin the complete `dist/` directory.

For custom frontend builds, `scripts/export-tornado-snapshot.mjs` and `scripts/prepare-tornado-cache.mjs` support preparing local public-history snapshots and updating the build's manifests. Generated history files stay in the ignored `history-export/` directory and are included in `dist/offline/` through `npm run prepare:offline`. `scripts/refresh-tornado-history.mjs` can refresh local snapshots using Saga and chain RPC reads without wallet signatures or transactions.
